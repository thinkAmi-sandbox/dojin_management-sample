# ValidationPipe統一リファクタリング計画

## 現状分析（2025-06-19調査結果）

### ✅ 既に導入済みの要素
- **ValidationPipe設定**: main.tsで設定済み（transform: true, enableImplicitConversion: true）
- **依存関係**: class-validator, class-transformerパッケージ導入済み  
- **DTOデコレータ**: 主要DTOでclass-validatorデコレータ使用済み
  - `CreatePrintingCompanyDto`: @IsNotEmpty, @IsUrl, @MaxLength適用済み
  - `CreateBookDto`: @IsNotEmpty, @IsString, @IsPositive適用済み
  - `CreateSubmissionDto`: @Transform, @IsInt, @Min等の高度な設定適用済み

### ❌ 問題のある箇所
- **コントローラーでの手動バリデーション混在**
  - 印刷所コントローラー: 137-184行目で手動バリデーション
  - 書籍コントローラー: 147-166行目で手動バリデーション
  - その他のコントローラーも要確認

### 確認済みコントローラー一覧
- PrintingCompaniesController: @UsePipes(ValidationPipe)使用 + 手動バリデーション併用
- BooksController: 手動バリデーションのみ
- SubmissionsController: ValidationPipe, @UsePipes確認済み
- AuthorsController: 要確認
- DeadlinesController: 要確認  
- DeadlineEditController: 要確認
- BookAuthorsController: 要確認

## 問題点

1. **手動バリデーションとValidationPipeの重複**
   - 同じバリデーション処理が手動とデコレータで二重実装
   - メンテナンス負荷の増大

2. **エラーハンドリング方式の不統一**
   - 手動バリデーション: renderでエラー表示
   - ValidationPipe: 例外投げる→要ハンドリング

3. **コード可読性・保守性の低下**
   - バリデーション処理がコントローラーに散在
   - ビジネスロジックとバリデーション処理の混在

4. **開発効率の問題**
   - 前回の入稿機能実装時にValidationPipe使用せず原因調査に時間を要した
   - 新機能追加時の一貫性確保が困難

### Phase 1: ValidationExceptionFilter作成 🔧 ✅ **完了**
**目的**: ValidationPipeから投げられるエラーをMPA用にハンドリング

**実装内容**:
- ✅ NestJSの`ExceptionFilter`を実装
- ✅ `BadRequestException`をキャッチしてEJSテンプレート用エラー形式に変換

- ✅ URLパスからテンプレート自動判定機能
- ✅ フォームデータを適切に戻すユーザビリティ保持

**作成ファイル**:
- ✅ `src/common/filters/validation-exception.filter.ts`
- ✅ `main.ts`でグローバルフィルター設定

**実装の特徴**:
- ValidationPipeのエラーメッセージをフィールド名ベースのerrorsオブジェクトに変換
