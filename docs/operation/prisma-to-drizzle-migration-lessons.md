# PrismaからDrizzle ORM移行作業の振り返り

## 概要

2025年6月14日に実施したPrismaからDrizzle ORMへの移行作業における課題、学び、改善点をまとめたドキュメントです。

## 🔍 技術的な課題と学び

### 1. データベース状態の管理

**問題**
- Dockerボリュームが残っていたため、コンテナを再作成してもPrismaの`_prisma_migrations`テーブルが残存
- `docker compose up -d`での再起動では不十分だった

**学び**
- ORM移行時は`docker compose down -v`でボリュームも削除する必要がある
- データベース状態のクリーンアップが移行成功の鍵

**改善点**
- 最初からボリューム削除を提案すべきだった
- データベース状態確認のステップを移行手順に明記

### 2. テスト環境の環境変数

**問題**
- テスト実行時に環境変数`DATABASE_URL`が正しく読み込まれず、デフォルトポート5432に接続を試行
- `ECONNREFUSED`エラーが発生

**学び**
- Vitestでは環境変数の読み込みが本番と異なる場合がある
- テスト実行時は明示的に環境変数を設定する必要がある場合がある

**改善点**
- テスト用の環境変数設定を事前に確認すべき
- テスト実行コマンドでの環境変数明示を検討

### 3. 段階的な実装アプローチ

**良かった点**
- TodoListで作業を体系化し、段階的に進めた
- 依存関係を意識した実装順序

**改善点**
- BooksController/ServiceがまだPrismaを使っていない状態でテストを先に更新してしまった
- 実装とテストの更新順序をより慎重に検討すべき

**学び**
- 依存関係の順序を意識した実装順序が重要
- 「スキーマ→サービス→コントローラー→テスト」の順序が適切

## 📝 プロセス面での気づき

### 4. コード品質チェックのタイミング

**問題**
- 実装完了後にlintエラーが発生（未使用変数、不要なasync等）
- 修正のための追加作業が発生

**改善点**
- 各ファイル作成・編集時に即座にlintチェックを実行すべき
- 「実装→テスト→lint→次の作業」のサイクルを確立

**学び**
- 継続的なコード品質チェックが効率的
- 後からまとめて修正するより、都度修正が効率的

### 5. テストファイルのフレームワーク統一

**問題**
- テストファイルでjestとVitestが混在していた
- モック関数の書き方で混乱が発生

**学び**
- プロジェクトのテストフレームワークを事前確認し、一貫性を保つ重要性
- 既存のテストファイルのパターンを踏襲することの重要性

**改善点**
- プロジェクト調査時にテスト設定も確認すべき
- テストフレームワークの差異を事前に把握

## 📚 学んだベストプラクティス

### ORM移行時の推奨手順
1. **事前調査**: 現状把握、依存関係確認、テスト環境確認
2. **環境準備**: データベース状態のクリーンアップ
3. **段階実装**: スキーマ→サービス→コントローラー→テストの順
4. **継続的検証**: 各段階でのlint・テスト実行
5. **ドキュメント更新**: 作業と並行したドキュメント更新
6. **最終確認**: 全テスト実行、ビルド確認

### 重要な教訓
> ORM移行のような大きな変更では「調査→計画→段階実装→検証」のサイクルをより厳密に守ることが重要

## 9. Drizzleマイグレーション対話式プロンプト問題（2025年6月25日追記）

**問題**
- `pnpm drizzle:generate`実行時に対話式プロンプトが表示される
- Claude Codeでは対話式入力に対応できず、コマンド実行が停止する
- スキーマ変更（pageCount削除、genre/seriesName/seriesNumber追加）時に発生

**具体的なケース**
```bash
pnpm drizzle:generate
> Is genre column in Book table created or renamed from another column?
❯ + genre             create column
  ~ pageCount › genre rename column
```

**学び**
- Drizzleはスキーマ変更時に自動的に対話式プロンプトを表示する
- Claude Codeの制限により、対話式プロンプトには対応不可
- ユーザー手動実行が必要なケースを事前に特定できる
- カラム追加/削除/変更を伴うスキーマ変更では高確率で発生

**改善点**
- スキーマ変更を伴う作業では、事前にマイグレーション生成をユーザー操作として分離
- Claude Codeには「実行すべきコマンドの提示」に留める
- マイグレーション生成後の作業（migrate実行、型チェック等）はClaude Codeが継続

**再発防止策**
- CLAUDE.mdに対話式プロンプト対応の注意事項を明記
- スキーマ変更作業時は必ずユーザー手動実行をアナウンス
- Claude Codeは「コマンド提示→ユーザー実行→結果確認→次ステップ」の流れを確立

**推奨される対話式プロンプト回答**
- 新規カラム追加: 「+ columnName create column」を選択
- カラム削除: 「- columnName drop column」を選択
- カラム名変更でない場合: 「create column」を選択（リネーム選択は避ける）

**適用後の効果**
- 同様の問題を事前に認識し、適切な対処法をガイド
- Claude Codeとユーザーの役割分担を明確化
- 作業効率の向上とユーザーストレスの軽減
